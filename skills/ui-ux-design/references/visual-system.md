# 视觉方向与设计系统

## 先读现有资产

识别项目已有的 Token、主题、组件和样式组织。修改只涉及局部时，复用现有语义与状态，不新建一套 `MASTER.md` 或 Token 文件。确实缺少全局设计决策时，再选与项目一致的存放位置。

新界面的视觉说明应落在实际内容上：哪些信息最重要，什么布局支持浏览或操作，字体是否适合中文和真实内容，颜色怎样区分动作与状态，动效表达什么变化。

“主题相关”和“看起来不同”是两回事。已有品牌、密集工作台和平台原生界面可以保持克制。用户指定的风格优先，不从一次任务推导长期审美偏好。

## Token 分层

原始值负责颜色、字号、间距等基础量；语义 Token 表达表面、正文、次要信息、主操作、危险、焦点等用途。组件只有存在独立覆盖需求时才增加组件 Token，避免为了三层结构增加无用间接层。

同一语义在主题或平台中映射到适合的值；不要假设 Web CSS 像素、iOS 点和 Android dp 可以直接复用。状态差异不只靠颜色表达。中文字体、回退、长文本与实际主题的对比度需要单独检查。

## 可选的离线检索

完整来源与运行示例见[快照索引](../../../tools/references/design-engineering/README.md)。快照缺失时仍可按本 Skill 执行，不能声称查询过本地数据库。

- 整体视觉方向使用 `--design-system`。
- 单点问题使用明确的 `--domain`，围绕一个可观察结果查询。
- 技术实现按检测到的栈使用单独的 `--stack` 查询；整体设计模式不接受栈参数时不要假定它已经处理平台约束。

查询词尽量短，英文数据优先用准确英文术语。检查结果身份与实际内容；相关词命中不等于解决了问题。没有匹配时可改写一次，然后明确说明缺口，不伪造匹配。

尤其检查：工作台是否被匹配为营销页、移动端推荐是否混入 Web 属性、字体是否支持目标语言、API 是否适用于当前版本。未经检查的结果不写入设计系统。

## 视觉验证

在目标布局范围检查真实文案、长文本、空数据、主题和关键状态。已实现的界面尽可能查看实际渲染图；只交付概念时标明其为方案，不把概念图作为运行证据。

视觉风格清单仅作灵感与校准，不对某种渐变、圆角、字体或布局作脱离任务的永久禁用。
