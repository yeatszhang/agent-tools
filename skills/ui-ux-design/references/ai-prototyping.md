# AI 辅助产品原型与视觉风格收敛

适用：新产品、视觉方向不明确或明确要求高保真原型。单点 UI 修复不触发完整流程。与平台实现、桌面 IPC/打包、Web 性能审查分工明确。

## 从需求到可验证界面

1. 明确目标用户、使用频率、主要任务、成功标志、输入设备、目标平台、内容密度；缺少真实证据时标记假设。
2. 视觉方向不明确且需要探索时，生成 2–3 个**结构上有差异**的候选（例如紧凑命令驱动工作台、导航优先多面板、偏原生桌面布局）。每个候选比较信息层级、操作路径、主题、可访问性和工程成本。无需为确定的小改动生成三版。
3. 可以按需用 Stitch/Figma/pen.dev 等构建概念图，React 项目也可用 v0 生成代码草案。但这些工具不证明可运行、性能或无障碍；不在项目中强制安装或使用，不把工具输出无条件合入现有框架。
4. 选定方向后，**优先复用项目既有 Design Tokens**；新项目确有必要时建立简短的 DESIGN.md（视觉意图、密度、字体/字重、色彩、间距、组件状态、平台差异和禁用误用范例）。具体值在项目实际 Token/CSS 中维护；不要双份可写的配置导致漂移。
5. 新产品需要验证共享组件与主题时，可先做 Component Gallery（按钮、输入、菜单、弹层、异步状态）；已有组件库或只交付视觉候选时无需另建。要求实现时，以一个可完成的端到端任务验证 MVP。
6. 运行目标应用：真实文案、长文本、Light/Dark、窗口尺寸、焦点/键盘、主流程与失败路径。截图检查内容和视觉一致性，交互测试检查可操作性；两者不可相互代替。

## Desktop 产品风格判断

- 可借鉴 Linear 的信息层级、Raycast 的快捷操作、macOS HIG/Windows Fluent 的平台交互，但不能复制商业产品 UI；“像 Linear”必须落到任务流、密度、间距、色彩和行为。
- 桌面工具通常比营销站更强调稳定布局、键盘焦点、可缩放分栏和高频效率。不要机械选择大圆角/高留白/强渐变，也不要把这些元素一律判错。
- 样式规范和组件库是两件事：shadcn/ui、Nuxt UI、PrimeVue 等仅提供组件实现；是否精致仍取决于内容层级、密度、交互细节和真实视觉验证。

## Skill 路由与验证证据

- 本文与 [视觉与 Token](visual-system.md)、[任务与状态](interaction.md) 一起属于 ui-ux-design；不单独创建 desktop-design Skill。
- Electron 窗口、快捷键与平台输入细节 → [client-ui-design](../../client-ui-design/SKILL.md)。
- Electron Main / Preload / IPC / 运行性能与真实桌面 E2E → [desktop-app-engineering](../../desktop-app-engineering/SKILL.md)。
- React Renderer 的 DOM/无障碍与性能审查 → [web-ui-review](../../web-ui-review/SKILL.md)。
- 概念图、截图、自动测试和真实用户验证是四种不同证据；报告时应区别，并说明未执行的环节。
- 其他 Skill 未随本目录安装时，按当前项目与平台资料完成对应工作，不将兄弟 Skill 视为运行前置依赖。
