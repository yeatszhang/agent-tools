# 任务与交互

产品任务模型是本地整理；并不代表上游提供了完整的用户研究方法。

## 最小任务模型

围绕本次任务填写必要内容，简单修改不必生成独立文档：

| 项目 | 要回答的问题 |
| --- | --- |
| 用户与情境 | 谁使用，频率如何，输入方式和环境有哪些限制？ |
| 触发与入口 | 从哪里开始，已有信息是否保留？ |
| 主流程 | 用户采取什么动作，系统给出什么反馈？ |
| 完成标志 | 用户怎样知道任务成功，下一步是什么？ |
| 失败与退出 | 重试、取消、返回如何处理？未保存输入是否丢失？ |

区分来源事实、设计假设和需要验证的判断。没有访谈或数据时，不虚构调研结论、成功率或用户偏好。

## 状态建模

仅对当前功能存在的状态建立对应关系：

| 状态 | 关注点 |
| --- | --- |
| 首次/空数据 | 说明当前情况，给出有意义的入口；不伪造数据 |
| 加载/提交中 | 明确正在进行的动作，避免重复副作用；耗时较长时考虑取消和进度 |
| 成功 | 给出与操作一致的结果反馈，保留下一步入口 |
| 可恢复错误 | 说明发生了什么、如何修复或重试，保留用户输入 |
| 权限/禁用 | 解释不能操作的原因和可行路径；不让控件表面可点却无响应 |
| 中断/返回 | 保留合理的导航与编辑上下文，按实际风险处理未保存变更 |

状态矩阵可放在现有规格、设计文件或组件文档中。项目使用 OpenSpec 时沿用相关规格/变更记录，不另建平行计划。

## 交互与文案

优先使用已有的语义控件和平台惯例。动作名称在入口、按钮、进度和结果中保持一致。错误与空状态提供具体方向；不以模糊的“出错了”或装饰性口号代替操作说明。

主任务需要键盘、触控或读屏时，检查对应输入方式；拖拽等手势应有适合该平台的可达替代。尺寸、单位和系统导航按目标平台处理。

## 任务验收

选一条真实主路径及当前改动涉及的失败路径，记录起点、动作和可观察结果。视觉截图与交互检查互相补充：截图不能证明提交、焦点、取消和恢复行为；测试通过也不能证明内容未被截断。
