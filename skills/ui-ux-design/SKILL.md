# UI/UX 设计

仓库共享约束见 [AGENTS.md](../../AGENTS.md)。本 Skill 为草案，尚未经真实产品验证。

## 目标与边界

交付能支撑用户完成任务的界面方案，并让任务、状态、视觉选择和验证结果相互对应。用户只要求方案时交付方案；要求实现时继续实现和验证，不把内部设计检查变成额外审批。

## 流程

1. 从现有页面、产品说明与用户要求提取：谁在什么场景完成什么任务、主操作、完成标志、平台和约束。缺少影响核心流程的信息时才提问；普通布局选择自行判断。未做用户研究的判断标为假设。
2. 读取现有品牌、设计 Token、组件和相关产品规格。先复用，再处理当前任务暴露的缺口；不要因上游推荐换字体、换组件库或引入新框架。
3. 先安排内容优先级与任务流，再定义涉及的加载、空数据、失败、成功、禁用和权限状态。只为实际存在的状态建模，参考[任务与交互](references/interaction.md)。
4. 对新增视觉方向说明颜色、排版、密度、布局和动效为何适合当前内容；沿用已有风格时只写差异。设计系统与检索资料见[视觉与 Token](references/visual-system.md)；需要从零探索多个视觉方案或让 AI 快速构建原型时，按需读取[AI 原型工作流](references/ai-prototyping.md)，不为局部修改强制跑完整流程。
5. 根据请求交付线框、交互说明或项目内实现。把主操作、反馈文案与状态实现连起来；产品动作使用用户能理解的名称。
6. 实现后检查目标视口和关键交互；能运行时查看截图、走一遍主流程，并检查键盘/读屏或对应平台能力。记录实际检查的环境和状态，未运行的部分明确列出。

## 设计判断

- 优先保证主任务清楚、状态可理解，再增加有意义的视觉差异；独特性不能替代可用性。
- 检索结果是候选。检查产品类型、界面类型、平台和版本；工作台不能直接套用落地页结构。
- 上游的配色、字体、动效和“反模板”示例不构成个人长期偏好。遵循本次用户要求与项目设计资产。
- 单点修复按问题范围处理，不为了一个按钮重新生成完整设计系统。

## 交付检查

说明完成了什么、关键设计理由、实际验证和剩余限制。方案应能回答主操作在哪里、结果如何反馈、失败如何恢复。触发与结果案例见 [evals](evals/README.md)。[来源与研究边界](../../docs/research/design-engineering.md)供追溯，不需要每次加载。
