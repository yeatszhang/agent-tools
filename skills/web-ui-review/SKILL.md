# Web UI 审查

仓库共享约束见 [AGENTS.md](../../AGENTS.md)。本 Skill 为草案。

## 流程

1. 从用户指定文件、页面或当前改动确定范围，识别框架、版本、组件库和可运行环境。已有明确目标时不重复询问路径。
2. 根据实际变化读取[审查要点](references/review.md)的相关部分。规则来源与离线快照见该参考；上游规则要经过适用性判断，不能直接覆盖用户与项目约定。
3. 检查代码中的触发条件和用户后果。静态代码能证明的问题直接定位；焦点、布局、读屏和性能等结论在能运行时用相应环境验证。
4. React/Next.js 性能问题先看请求依赖和包体积，再看渲染与计算。优化前后保持同一测试条件；无测量时不声称收益。
5. 输出按影响排序的可行动问题，每条包含文件行号、触发条件、用户影响和修复方向。区分已证实问题、待验证疑点和可选审美建议。
6. 用户只要求审查时不改代码；要求修复时在授权范围内修复并复查。没有发现问题时写明检查范围和验证缺口，不宣称全面合规。

## 判断边界

- 原生语义控件已有的键盘行为不应再被判为“缺少手写键盘事件”。先查控件语义，再看自定义交互。
- 外部规则中的字体、大小写、标点、数值门槛与库选择不自动成为缺陷。只有违反明确要求或产生可证明后果时才报为问题。
- 组件组合和性能规则必须匹配版本与场景，不为简单组件强加 Provider，不机械增加 memo/useCallback 或依赖库。
- 审美判断与功能缺陷分开。浏览器截图不能证明读屏、焦点恢复和操作正确；静态源码也不能证明实际性能。

## 验证

核对每条发现的代码位置与可复现条件；性能结论带测量条件。触发与结果评测见 [evals](evals/README.md)。
