# React / Next.js 本地审查步骤

适用于界面性能与组件 API 审查。依据仓库保存的 [Vercel 性能规则](../../../tools/references/design-engineering/upstream/agent-skills/skills/react-best-practices/SKILL.md)和[组合规则](../../../tools/references/design-engineering/upstream/agent-skills/skills/composition-patterns/SKILL.md)提炼；本地调整为按用户问题取证的流程，不逐条照搬上游规则，也不将规则适用于所有版本。

## 从用户路径定位

1. 写明慢在哪里：首次进入、筛选、输入、列表滚动或弹层操作。读项目版本、路由和组件边界，找到对应的数据入口与状态更新；只有实际涉及服务端组件时才分析其边界。
2. 沿调用关系记录请求何时开始、依赖哪个结果、在哪里等待。独立工作可评估并行；依赖用户身份、前一步数据或事务顺序的工作保留顺序。并行改动同时检查失败、取消和过期结果覆盖问题。
3. 检查首屏实际加载的模块与资源。只有低频或非关键模块才考虑延后加载；明确延后后显示什么、失败如何恢复。不能仅凭 import 写法判定实际打包体积，需看当前构建结果。
4. 追踪一次交互影响的 state、订阅与渲染范围。先排除重复请求、宽泛订阅、重复昂贵计算，再根据 Profiler 证据选择拆分或缓存；不机械添加 memo、useMemo、useCallback。
5. 列表规模、图片尺寸或布局计算影响交互时，使用真实数据检查。虚拟化还要验证键盘焦点、滚动定位和项目高度变化；静态短列表不为符合规则换实现。

## 组件组合与版本

- 列出组件被调用的实际状态组合。多个布尔参数能形成无效状态时，评估显式变体或组合 API；只被单处使用的简单组件无需为了模式增加 Provider。
- 检查状态由谁持有、事件由谁处理，避免相同数据在多处独立更新。拆分组件后保留原有焦点、名称、错误反馈和调用方兼容性。
- 按项目已有 React / Next.js 版本判断 API；审查不顺带升级框架。涉及实验动效、服务端能力或缓存 API 时，再核对目标版本的官方资料；无法核实时保留待验证项。

## 交付与复验

对每项发现记录文件行号、触发路径、用户影响和建议；区分静态可证明的行为与需要运行的性能假设。修复后在相同构建模式、设备、数据规模下重复原路径，报告使用的网络时间线、Profiler 或构建分析证据。没有基线与复测，不填写性能收益；源码与截图不能代替实际焦点、读屏和交互验证。
