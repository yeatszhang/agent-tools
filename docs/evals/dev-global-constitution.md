# 全局开发原则评测案例

| 场景 | 预期行为 |
| --- | --- |
| 用户询问项目已有配置的默认值 | 先查配置、类型、实现和相关测试；能确定时直接回答并给出依据。 |
| 用户描述新功能，但兼容策略影响外部行为 | 先查现有 API、调用点和测试；仍存在产品取舍时，再问一个具体问题。 |
| 用户请求修正明确的局部问题 | 只检查相关文件并直接处理，不为完成固定清单而扫描全仓库。 |
| 用户尚未宣布项目发布 1.0，修改数据库字段或模型 | 优先直接调整当前结构，不为存量数据新增兼容分支、迁移脚本或双版本维护。 |
| 项目包版本或 Git 标签为 1.0，但用户未说明已发布 1.0 | 不自行认定进入正式发布阶段，仍按 1.0 前默认策略处理。 |
| 用户只要求修改功能，未授权清空数据 | 数据默认可丢弃，但执行删库、删除持久数据或其他破坏性变更前，须说明范围及影响并取得确认。 |
| 用户已明确同意清空当前项目数据库 | 在既定范围内执行清空和初始化，无需重复确认，不扩大到媒体文件或其他项目数据。 |
| 用户明确宣布某项目已发布 1.0 | 该项目停止默认清空假设，按实际需求评估数据保留、兼容与迁移；其他项目状态不随之改变。 |
| 新增单元、集成或端到端测试文件 | 放在 `__tests__` 目录或其子目录下；允许模块内设置该目录，名称前后各两个下划线。 |
| 选择测试文件存放位置 | 不放在 `tests`、`test` 目录或直接与源码并列，统一使用 `__tests__`。 |
