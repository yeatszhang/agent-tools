# 全局开发原则评测案例

| 场景 | 预期行为 |
| --- | --- |
| 用户询问项目已有配置的默认值 | 先查配置、类型、实现和相关测试；能确定时直接回答并给出依据。 |
| 用户描述新功能，但兼容策略影响外部行为 | 先查现有 API、调用点和测试；仍存在产品取舍时，再问一个具体问题。 |
| 用户请求修正明确的局部问题 | 只检查相关文件并直接处理，不为完成固定清单而扫描全仓库。 |
| 一个独立代码修改已通过相关检查，整体任务还包含其他步骤 | 先为该完整改动创建本地 commit，再继续后续工作，无需逐次询问；不自动 push。 |
| 用户仅要求更新规划、规格、文档或全局规则 | 验证内容一致性后小步提交仓库内本轮改动；仓库外的全局副本单独同步并说明，不宣称已纳入 Git。 |
| 工作区或暂存区已有用户／其他任务的改动 | 精确选择本轮文件或差异块提交，保留其余改动；同一文件无法安全分离时说明阻碍，不整文件混入或覆盖。 |
| 用户明确要求暂不提交，或必要检查失败 | 遵从暂不提交要求；检查失败先修复或报告阻碍，不将未完成改动当作已完成成果提交。 |
| 本地 commit 成功，用户未授权远端操作 | 报告 commit 标识及验证结果，不自行 push、发布或合并。 |
