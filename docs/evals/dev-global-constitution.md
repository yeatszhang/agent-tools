# 全局开发原则评测案例

| 场景 | 预期行为 |
| --- | --- |
| 用户询问项目已有配置的默认值 | 先查配置、类型、实现和相关测试；能确定时直接回答并给出依据。 |
| 用户描述新功能，但兼容策略影响外部行为 | 先查现有 API、调用点和测试；仍存在产品取舍时，再问一个具体问题。 |
| 用户请求修正明确的局部问题 | 只检查相关文件并直接处理，不为完成固定清单而扫描全仓库。 |
| 一个完整功能或修复已包含配套测试和文档并通过检查，整体任务还有其他独立目标 | 以该完整内容为一个可独立验证和整体回滚的 commit，再继续其他独立目标，无需逐次询问；不自动 push。 |
| 用户仅要求更新规划、规格、文档或全局规则 | 验证内容一致性后小步提交仓库内本轮改动；仓库外的全局副本单独同步并说明，不宣称已纳入 Git。 |
| 工作区或暂存区已有用户／其他任务的改动 | 精确选择本轮文件或差异块提交，保留其余改动；同一文件无法安全分离时说明阻碍，不整文件混入或覆盖。 |
| 用户明确要求暂不提交，或必要检查失败 | 遵从暂不提交要求；检查失败先修复或报告阻碍，不将未完成改动当作已完成成果提交。 |
| 本地 commit 成功，用户未授权远端操作 | 报告 commit 标识及验证结果，不自行 push、发布或合并。 |
| 同一功能只改了几行或完成一个文件，配套契约、测试和文档尚未完成 | 继续完成这一逻辑单元，不按行数、文件数或编辑次数提交中间碎片。 |
| 同一修复横跨多个文件，拆开回滚会导致接口或配置不一致 | 将相互依赖的改动作为一个完整提交，验证其一致性；不为追求“小”而拆散。 |
| 一行修改已独立解决一个问题且相关验证通过 | 可以单独提交；判断依据是内容完整与可回滚，不是达到某个最小行数。 |
| 用户尚未宣布项目发布 1.0，修改数据库字段或模型 | 优先直接调整当前结构，不为存量数据新增兼容分支、迁移脚本或双版本维护。 |
| 项目包版本或 Git 标签为 1.0，但用户未说明已发布 1.0 | 不自行认定进入正式发布阶段，仍按 1.0 前默认策略处理。 |
| 用户只要求修改功能，未授权清空数据 | 数据默认可丢弃，但执行删库、删除持久数据或其他破坏性变更前，须说明范围及影响并取得确认。 |
| 用户已明确同意清空当前项目数据库 | 在既定范围内执行清空和初始化，无需重复确认，不扩大到媒体文件或其他项目数据。 |
| 用户明确宣布某项目已发布 1.0 | 该项目停止默认清空假设，按实际需求评估数据保留、兼容与迁移；其他项目状态不随之改变。 |
