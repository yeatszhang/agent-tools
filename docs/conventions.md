# Conventions

## Skill 设计

一个 Skill 应回答四件事：

1. 什么时候触发。
2. 核心工作流是什么。
3. 哪些规则必须遵守。
4. 如何验证输出是否变好。

`SKILL.md` 保持短小。大段规则、样例、场景说明放到 `references/` 和 `examples/`。

## 引用与本地副本

遵循 [AGENTS.md](../AGENTS.md) 的本地优先原则：

- 当前任务必需的流程、判断条件和验收步骤写入仓库；长内容放对应 Skill 的 `references/`，不要只留外链或要求先加载另一个 Skill。
- 内容、适用范围或验收方式有差异时，保留完整的场景化版本，允许与其他资料重叠；不能只留差异片段，迫使执行时跨文档拼装。
- 只有内容和适用范围完全相同才优先共享引用。例如上游逐字快照、同一份仓库政策；`CLAUDE.md` 继续链接权威 `AGENTS.md`。
- 本地改写注明来源、适用范围及本地调整；原文快照保持原样。上游更新时审查差异，再决定是否同步本地版本，不用上游直接覆盖场景化内容。
- 外链用于溯源、拓展和核对版本化 API。未读取的来源不能视为已验证；网络不可用时，本地步骤仍应足以完成已有证据支持的分析，依赖当前 API 的实现结论标记待核实。
- 验收时检查：只读当前 Skill 及其本地参考，能否得到具体执行和验证步骤；共享引用是否确为完全相同的内容；场景差异是否被保留。结构检查不等于行为评测。

## 学习型 Skill

长期偏好分为三层：

- `candidate`：一次观察。
- `emerging`：多次出现但证据仍不足。
- `stable`：经过重复观察和 eval，进入默认行为。

不要让 Agent 因单次改动直接重写稳定规则。

## MCP

仓库只维护：

- server 名称
- 官方/上游地址
- transport
- command/url 模板
- 所需环境变量名
- 使用场景
- 本地启用状态说明

永远不提交真实 token / key。

## Evals

每次升级 Stable Rule，至少补一个 case。

优先观察：

- 事实是否保持
- 原始判断是否保持
- AI-pattern 是否减少
- Voice 是否一致
- 人工二次修改量是否下降
